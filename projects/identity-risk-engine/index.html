Identity Risk Engine

Account-takeover detection for Zero Trust access

A streaming User & Entity Behaviour Analytics engine. It scores every login and app access against the user’s own baseline and their role’s peer group, explains why an event looks risky, and returns a Zero Trust decision: allow, step-up MFA, or block and alert.

[01] ~/the-problem

Why it matters

Stolen or weak credentials are consistently among the top ways attackers get in. Static rules such as “block country X” are either too noisy or too easy to evade.

This engine applies “never trust, always verify”: every event is judged in context. Is this normal for this user? Is it normal for people in this role? Is it even physically possible?

A sales rep opening iam_admin, or Pune → Moscow in 20 minutes, should never look the same as a normal Tuesday login.

[02] ~/how-it-works

How it works

Seven explainable detections feed one risk score; an unsupervised model can only escalate when an explainable signal agrees.

  1. 01

    Baselines that only look back

    Per-user and per-role baselines (countries, devices, hours, download volume) are built from past events only, so scoring is streaming and leak-free.

  2. 02

    Seven detections

    Credential stuffing, MFA fatigue, impossible travel (>1,000 km/h), session hijack, privilege misuse (<5% of peers), data exfiltration (>10× p95), dormant account takeover.

  3. 03

    Explainable risk fusion

    Risk = 100 × (1 − Π(1 − wᵢ)), so independent signals compound naturally and every score comes with its reasons.

  4. 04

    Corroborated anomaly score

    An Isolation Forest scores the same features but may only escalate an event when at least one explainable signal agrees. That keeps alert fatigue low.

  5. 05

    Anti-poisoning

    Blocked activity never updates the baseline, so an attacker can’t “teach” the model that Moscow is normal.

  6. 06

    Zero Trust decision via API

    FastAPI endpoint for an IdP / SSO hook returns allow, step_up_mfa or block_and_alert with human-readable reasons.

$ curl -X POST localhost:8002/evaluate -d '{"user":"u0007","role":"sales","city":"Moscow"}'
{"risk": 99.2, "decision": "block_and_alert",
"reasons": ["impossible_travel", "brute_force", "hosting_asn"]}

[03] ~/threat-coverage

Threat coverage

Each detection mapped to the MITRE ATT&CK technique it targets.

T1110.004Credential stuffing

Burst of failed logins, failures from several countries, a hosting-provider network and a new device.

T1621MFA request generation

3 or more MFA denials in 30 minutes followed by an approval (push bombing).

T1078Valid accounts

Impossible travel (>1,000 km/h), a dormant account used after 21+ days, an app used by <5% of the role’s peers.

T1550.004Web session cookie

Hosting network + new device + new country in the middle of a session (token replay).

T1567Exfiltration over web service

Download >10× the user’s 95th percentile or z-score > 3, off-hours.

The rules are already strong on this data. The hybrid lifts PR-AUC from 0.960 to 0.976 by ranking real attacks above borderline benign events, at the cost of about 0.6 extra benign alerts a day.

Speed: scoring all 111,066 events in a single pass takes 0.07 ms per event at the median (p99 0.12 ms), so the rules engine adds no noticeable delay to a login. Measured on a 2-core cloud workspace.

HONEST LIMITS

— The dataset is synthetic (real identity logs are confidential), and the attack scenarios were written alongside the detectors. Treat the numbers as end-to-end proof, not a real-world benchmark.

— The Okta adapter is checked against a documented-format sample and unit tests, not a live tenant; thresholds and the hosting-network list would need tuning.
