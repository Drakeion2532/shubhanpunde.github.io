[01] ~/the-problem

Why it matters

Lab programs are usually checked by eye on one example, so bugs survive into the final submission and into the code students copy later.

Here every program runs against known textbook answers, and each CPU scheduler is compared with a Python reference on 200 random workloads, so any mismatch shows up immediately.

Writing the tests turned up real bugs in the original lab code; each fix is commented in the source.

[02] ~/how-it-works

How it works

Classic algorithms, each with automatic proof that it gives the right answer.

  1. 01

    CPU scheduling

    FCFS, SJF, SRTF, two priority variants and Round Robin print completion, turnaround and waiting times for every process.

  2. 02

    Disk scheduling

    FCFS, SSTF and C-SCAN on the textbook queue 98, 183, 37, 122, 14, 124, 65, 67 with the head at 53.

  3. 03

    Page replacement

    FIFO, LRU and Optimal (Belady) on the 20-reference textbook string with 3 frames: 15, 12 and 9 faults.

  4. 04

    Deadlock avoidance

    The Banker's algorithm finds the safe sequence P1 → P3 → P4 → P0 → P2 and reports unsafe states as unsafe.

  5. 05

    Shell scripting

    Bash scripts for primes, reversal and bubble sort, plus a Linux command worksheet.

  6. 06

    Real-world link

    Each lab notes where the idea runs today, from Linux's EEVDF scheduler to Multi-Gen LRU and the mq-deadline disk scheduler.

HONEST LIMITS

These are textbook versions: real kernels add priorities, aging and per-CPU queues that the labs leave out.

Programs read input interactively, so the tests feed them fixed inputs; there is no GUI.
